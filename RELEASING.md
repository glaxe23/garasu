# Как выпустить новую версию Garasu

Инструкция для того, кто выпускает релиз (человек или ИИ-помощник с доступом к этому репозиторию). Её достаточно, чтобы выпустить версию без дополнительного контекста.

## Как это устроено

- Выпуск полностью автоматический: workflow [`.github/workflows/garasu-release.yml`](.github/workflows/garasu-release.yml).
- **Триггер выпуска — изменение `files/theme/version.txt` в ветке `main`.** Другие пуши в `main` (README, документация) релиз не запускают. Pull request в `main`, который трогает `files/**`, только собирает и проверяет установщик, но не публикует его.
- Workflow на Windows собирает `Garasu-Setup.exe` и `Garasu.zip` скриптом `scripts/build_release.py` и сам их проверяет. Потом создаёт релиз с тегом `Garasu_v<версия>` и заголовком `Garasu <версия>`, к которому прикреплены оба файла.
- Описание релиза workflow делает автоматически (`--generate-notes`, это просто список коммитов). Нормальный текст «что нового» после выпуска вставляется отдельно (шаг 6).
- Программа обновляется у пользователей сама: кнопка «Обновить» в панели «Темы» (`files/theme/update.py`) сравнивает `version.txt` с тегом последнего релиза на GitHub и скачивает **архив исходников этого тега** (`zipball_url`), а из него берёт папку `files/`. Значит, при обновлении пользователи получают ровно то, что лежит в репозитории на момент тега. Поэтому номер версии должен только расти, а в репозиторий нельзя класть ничего личного (см. ниже).

## Формат версии

`version.txt` — одна строка без перевода строки: `1.6`, `1.7` или `1.6.1`. Шаблон проверки: `^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)(\.(0|[1-9][0-9]*))?$`. Тег `Garasu_v<версия>` не должен уже существовать, иначе публикация упадёт.

## Шаги выпуска

1. **Взять свежий `main`.** Работать от `origin/main`, в отдельной ветке, например `release-1.7`.
2. **Перенести изменения.** Код программы лежит в `files/` (`files/theme` — Python и PowerShell, `files/zebar` — HTML-виджеты, `files/install.ps1` и `files/uninstall.ps1` — установка и удаление). Бери только изменения программы. **Не коммить личное и временное** (список ниже).
3. **Проверить, что код запускается хотя бы синтаксически:**
   ```
   python -c "import ast,glob;[ast.parse(open(f,encoding='utf-8').read(),f) for f in glob.glob('files/theme/*.py*')]"
   ```
4. **Собрать установщик локально** (так же, как в CI; нужны Python 3.13 и `pip install Pillow==12.0.0`):
   ```
   python scripts/build_release.py --output dist
   ```
   В конце должно быть `Verified Garasu-Setup.exe and Garasu.zip (N package files)`. Загляни в `Garasu.zip`: новые файлы на месте, личных файлов нет. Папку `dist/` не коммить.
5. **Поднять версию и опубликовать.** Записать новый номер в `files/theme/version.txt` (без перевода строки), при желании дописать новое в `README.md` (раздел «Что внутри»), закоммитить и отправить в `main` (`git push origin <ветка>:main`). Workflow стартует сам. Дождаться, пока зелёными станут обе задачи, `build` и `publish` (обычно 5–10 минут), и проверить, что в релизе есть оба файла.
6. **Вставить описание «что нового».** Текст на русском, для обычных пользователей, сгруппировать по разделам: новое, виджеты, исправления. Образец — описание релиза `Garasu_v1.6`. Вставить можно в веб-интерфейсе (Edit release), командой `gh release edit Garasu_v<версия> --notes-file notes.md` или через API: `PATCH /repos/glaxe23/garasu/releases/{id}` с полем `body`.

## Что нельзя коммитить

- Пользовательские данные и настройки: `settings.json`, `state.json`, `panel_pos.json`, `theme.json`, `widgets.json`, `nowplaying.json`, `tasks.json`, `photos.json`, `calendar_notes.json`, `schedule.json`, `pomodoro_state.json`, `zpack.json`, `gifwall.json`, `.env`. Сборка их и так выкидывает, но в репозиторий они тоже не должны попадать.
- `files/zebar/scratch.txt` должен оставаться **пустым** (это черновик пользователя в виджете).
- `files/glazewm-config.yaml`: цвет рамки окна (`color` около строки 64) — это значение по умолчанию `'#f9b7a1'`. Цвет от темы, которая сейчас стоит у разработчика, не коммитить.
- `files/theme/islands.base.yaml`: `image_path: "."`, а не чей-то личный путь вроде `C:/Users/<имя>/Pictures`.
- `files/theme/themes.json`: только общие темы, обои которых лежат в комплекте. Личные темы (например, видеообои, которых нет в репозитории) не добавлять.
- Временные файлы: `*.log`, `*.before-clean`, `__pycache__/`, `thumbs/`, `videocache/`, `gifwall_*.png`, `dist/`.
- Ключи, токены, пароли — никогда.

## Если что-то пошло не так

- **`build` упал:** открыть лог задачи в Actions и исправить. Релиз при этом не создаётся, можно чинить и пушить снова, не меняя версию.
- **`publish` упал, потому что тег уже есть:** поднять версию ещё раз (например, `1.6.1`).
- **В релиз попал лишний или личный файл:** выпустить следующую версию без него. Удалять уже опубликованный релиз — только с разрешения владельца.
